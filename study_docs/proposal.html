Reinforcement learning for crop-row flight stabilization

A simulated quadrotor learns to fly a crop row at fixed altitude and reject wind gusts — a real, largely unsolved precision-agriculture control problem, tackled with deep RL in a physics-accurate simulator. Three policy-gradient algorithms (PPO, REINFORCE, A2C) are compared on one shared environment.

01

Necessity

Precision agriculture leans on drones for crop monitoring, but reliable low-altitude flight over crop rows under wind disturbance is still an open control problem outside expensive commercial autopilots. Hand-tuned control is brittle: it has no way to adapt beyond the rules it was given.

🌾

Precision ag needs it

Row-level crop monitoring by drone is only useful if flight is stable enough to trust the imagery.

💨

Wind is the hard part

Disturbance is random and continuous — a fixed control law can't be tuned for every gust.

🤖

RL adapts, PID doesn't

A learned policy can correct for disturbance patterns it was trained on, not just the one case it was tuned for.

🧪

Sim-first, honestly scoped

MuJoCo lets us iterate before any physical flight test, while we openly acknowledge the sim-to-real gap.

⚠️

Our own baseline already proves the point. The hand-coded altitude-hold controller holds altitude to 1.0 cm of error on average — genuinely excellent — yet it never once reaches the end of the row in 20 held-out evaluation episodes, because a fixed PD law has no mechanism to correct lateral drift or push forward. That gap is exactly what a learned policy needs to close.

02

Proposal

AgriFlight-RL trains a policy to fly a simulated quadrotor along a crop row at a fixed 1.2 m, staying on the centreline and making forward progress despite continuous random wind. The policy outputs four high-level commands and a fixed inner controller drives the rotors. We formulate it as an MDP, solve it with deep RL, and compare three policy-gradient algorithms on one shared environment and reward. Click a stage to see what's inside it.

04

RL tools to achieve the outcome

The pipeline from physics to a trained policy, in order. Click a stage for the library and the theory behind it.

MuJoCo (rigid-body dynamics + contact solver) running the Skydio X2 quadrotor model from Google DeepMind's mujoco_menagerie (Apache-2.0). Gives us realistic thrust, drag and tilt dynamics without deriving the equations of motion ourselves. It does not model rotor ground effect or canopy turbulence, which we state as a limitation.
Gymnasium standardises reset() / step() / observation & action spaces so any RL library plugs in. Registered as AgroDrone-v0: 14-dim observation, 4-dim action, 25 sanity tests pass. Env v1 (steps 3–5) was merged into main on Thu 24 Sep and is now fixed: interface changes go through Juan, so all three algorithms train on one identical environment.
The policy outputs 4 commands — forward velocity, lateral velocity, climb rate, yaw rate, normalised to [-1, 1]. A fixed, non-learned inner PD attitude/rate controller turns them into the four rotor thrusts, using the drone's real mass, inertia and rotor geometry. Why: learning to hover from raw motor commands is a much harder sub-problem than the one we are studying. Tests cover velocity tracking, climb and yaw hold. Owner: Juan.
One reward shared by all three algorithms: −(w1·height² + w2·lateral² + w3·tilt² + w4·action²) + w5·Δs_along_row + survival − crash + completion, with every weight in one RewardConfig. Squared errors punish big deviations harder; w5 rewards progress along the row so hovering in place is not a degenerate optimum (a test checks that finishing the row beats hovering). Defaults are first-pass and untuned; tuning is Stage 2, and flights must be watched for reward hacking. Owner: Juan.
L0 no wind, on the row, altitude hold · L1 no wind, offset spawn, row following · L2 steady lateral wind · L3 gusting wind · L4 gusting wind with free yaw. Chosen with gym.make("AgroDrone-v0", level=k). Fixed before tuning and never adjusted per algorithm; results are the highest level each one clears plus the samples needed. Owner: Juan.
A P controller holding altitude through the climb-rate command, and random commands as the floor. They define the gap a learned policy has to close (Section 3). A third, stronger cruise-and-centre controller (forward, sideways = −offset, altitude hold) finishes the row every time, so we propose adding it as a baseline.
Same environment, reward and Gaussian policy head for continuous actions. REINFORCE (Juan): Monte-Carlo policy gradient — simple but high variance. A2C (Panzhao): adds a learned critic as baseline to cut variance. PPO (Nelkit): clipped objective keeps each update near the previous policy, with GAE for advantages. We expect REINFORCE to struggle; that is a valid comparative finding.
PPO uses CleanRL's single-file ppo_continuous_action.py copied into the repo, because the pip cleanrl 0.4.8 wrapper fails on import. REINFORCE and A2C are written directly in PyTorch following the subject's policy-gradient content. Each runs one L0 episode without crashing by Fri 2 Oct.
Training runs on AWS SageMaker, with Google Colab as fallback. TensorBoard gives live curves, Matplotlib the report figures, and everything is consolidated into one Colab notebook for the demo. None of this is set up in the repo yet.
evaluate_policy.py runs seeded episodes and reports reward, crash rate, completion and altitude error. Still to add (Panzhao): multi-seed runs, per-level results, training stability, sample efficiency and the REINFORCE vs A2C vs PPO comparison charts.
If an algorithm shows no upward reward trend within 1M steps: reuse the furthest-along algorithm's validated weights, cut tuning cycles, and ease the task (weaker wind, fixed yaw, closer spawn, wind curriculum). We do not switch environment or algorithm family. Last resort: demo altitude-hold flying in 3D, reported honestly.
